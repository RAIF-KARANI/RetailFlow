The computer-vision pipeline stays on the host because it needs the GPU directly.
The three services run in Docker. All ports are bound to `127.0.0.1` only.

## 1. Run it

```powershell
docker compose up -d --build                      # db + api + dashboard
python run.py --source data/caviar/TwoEnterShop1front/TwoEnterShop1front.mpg `
              --scene scenes/caviar_front.json --api http://127.0.0.1:8000
# dashboard: http://localhost:3001     API docs: http://localhost:8000/docs
```

Ports: the dashboard is on **3001** (3000 is often used by other dev servers; change it
with `DASHBOARD_PORT`), and Postgres is on host port **55432**.

## 2. Data model (`backend/app/schema.sql`)

| Table | One row per | Key columns |
|---|---|---|
| `cameras` | camera | `camera_id`, `scene` (the scene JSON: line, zones, profile, staff rule) |
| `sessions` | pipeline run on one source | `session_id`, `camera_id`, `source`, `video_fps`, `run_info`, `summary` |
| `events` | analytics event | `session_id`, `frame`, `ts`, `type`, `track_id`, `direction`, `zone`, `value`, `staff` |
| `heatmaps` | session | `grid` (person-seconds), `cell`, `floor`, `background` (PNG) |
| `people_samples` | session, second | `now` (people in view, mean over the second), `total` (people so far: track IDs seen ≥ 3 s) |

**Why sessions:** each dataset video has its own timeline starting at 0 s and no real
clock time. A session keeps every time on **its own video timeline**, and the dashboard
labels axes as video time. Sessions are never merged onto an invented clock.

**Retroactive exclusion:** the `customer_events` view drops **every** event of a track
that has a `staff_flag` or `static_flag` event, including events from before the flag.
All customer numbers come from this view.

**Occupancy is rebuilt from visits.** `zone_enter` carries the visit's real start time
and `zone_exit` its real end time (plus dwell). The API pairs them into visits and computes
time-weighted occupancy per bucket (`backend/app/analytics.py`). This is why the pipeline
does not send occupancy samples: a sample cannot be corrected later when a track turns
out to be staff or a mannequin. An enter without an exit is a visit in progress, counted
in "in zone now".

**Privacy:** the database holds only integer track IDs, positions, zone names, times and
flags. The only image is the heatmap background: the per-pixel median of 15 frames sampled
2 s apart, which removes people who move. Someone standing still for the whole sample
could remain visible, so for real deployments the background should be taken from an
empty-store frame.

## 3. API

| Method | Path | Used by | Purpose |
|---|---|---|---|
| GET | `/api/health` | ops | database reachable |
| PUT | `/api/cameras/{id}` | pipeline | register / update the camera's scene |
| DELETE | `/api/cameras/{id}` | ops, tests | remove a camera and all its data |
| POST | `/api/sessions` | pipeline | start a session → `session_id` |
| POST | `/api/sessions/{id}/events` | pipeline | batch of events (unknown types → 422) |
| POST | `/api/sessions/{id}/people` | pipeline | people in view / total people, one sample per second |
| POST | `/api/sessions/{id}/finish` | pipeline | summary, heatmap grid, background PNG |
| GET | `/api/cameras` | dashboard | cameras with customer totals over all sessions |
| GET | `/api/cameras/{id}/sessions` | dashboard | sessions with totals |
| GET | `/api/sessions/{id}/summary` | dashboard | IN/OUT (customers and all), staff/static tracks, dwell per zone |
| GET | `/api/sessions/{id}/counts?bucket_s=10` | dashboard | IN/OUT per bucket |
| GET | `/api/sessions/{id}/occupancy?bucket_s=5` | dashboard | average people per zone per bucket |
| GET | `/api/sessions/{id}/people?bucket_s=5` | dashboard | people in view (mean) and total so far per bucket |
| GET | `/api/sessions/{id}/heatmap` | dashboard | grid + metadata |
| GET | `/api/sessions/{id}/background.png` | dashboard | people-free background |

Interactive documentation is generated by FastAPI at `/docs`.

Packages: `fastapi`, `uvicorn` (its server) and `psycopg` (the PostgreSQL driver), all pinned in
`backend/requirements.txt`. Plain SQL is used; there is no ORM.

## 4. Sender (`retailflow/sender.py`)

- Standard library only (`urllib`), so the pipeline needs no new packages.
- Registers the camera, opens a session, then posts events in batches (every 200 events or 1 s).
- **If the API is down:** events stay in memory, and the next attempt is after 5 s (not on
  every event). If more than 100,000 are waiting, the oldest are dropped and counted
  (`events_dropped` in the summary). `events.csv` is always written locally as well.
- `localhost` is rewritten to `127.0.0.1` (see TROUBLESHOOTING: a 2 s delay per request otherwise).

## 5. Dashboard (`dashboard/`)

Next.js (App Router, TypeScript). Its only dependencies are `next`, `react` and `react-dom`.
Charts are plain SVG and the heatmap is a `<canvas>`, so there is no chart library.

| Page | Shows |
|---|---|
| `/` | Every camera: sessions, video analysed, customers in/out, zones; **+ Add camera** button |
| `/cameras/new` | Add camera, step 1: name the camera and upload its video (needs the runner, below) |
| `/setup/[id]` | Step 2: draw the counting line, the IN side and zones on one frame (any frame number), save `scenes/<camera>.json`, then **Start live** for N minutes (0 = until stopped) |
| `/cameras/[id]` | Live video of the running pipeline on the page (heads pixelated) with a **Stop** button; session picker; KPIs (customers in/out, crossings excluded as staff/static, video length and model); IN/OUT per bucket; zone occupancy over time; dwell table (visits, mean, median, longest, in zone now); heatmap over the background |

- A session that is still running is marked **live** and refreshes every 5 s.
- Every time axis is **video time (m:ss)**. There are no business hours, because the data has none.
- Light and dark mode follow the system setting.

### Add camera from the dashboard: the host runner (`runner.py`)

The pipeline needs the GPU, so it runs on the host, not in Docker. `python runner.py` starts a small
standard-library server on `127.0.0.1:8095` that the dashboard calls:

| Endpoint | Does |
|---|---|
| `POST /api/cameras/<cam>/video?filename=x.mp4` | Body = the raw video. Saved to `data/uploads/<cam>.<ext>` after OpenCV decodes 2 frames. An existing upload is replaced only with `&replace=1`. Up to 8 GB |
| `GET /api/cameras/<cam>/frame?n=50` | One frame as JPEG, for drawing |
| `GET`/`PUT /api/cameras/<cam>/scene` | Read (or a default) / save `scenes/<cam>.json`, checked by `retailflow.config` |
| `POST /api/cameras/<cam>/start` `{"minutes": 5}` | Loops the video as `rtsp://127.0.0.1:8554/<cam>` (`tools/simulate_rtsp.py`, as `demo.ps1`), then `run.py --api --preview <free port 8090-8109> --blur-heads`, outputs in `outputs/web/<cam>/` (log: `run.log`) |
| `POST /api/cameras/<cam>/stop` | The preview's Stop (outputs and summary saved as normal); force after 30 s |
| `GET /api/cameras/<cam>/run` | starting / running / stopping / finished / failed, preview URL, last log lines |

- Listens on 127.0.0.1 only; writes are refused from any origin other than the dashboard's (`RUNNER_ORIGINS`).
- Camera names: letters, digits, `_`, `-`, up to 48 characters (no paths).
- Runs are kept in memory: restarting the runner asks its runs to stop.
- Tests: `tests/test_runner.py` (upload, frame, scene save, bad input, other origins).

## 7. Not done (scope)

- No authentication. The services listen on `127.0.0.1` only. A real deployment needs auth and TLS.
- One database connection per request (fine for a demo; a connection pool for production).
- No data retention policy yet. Sessions can be deleted per camera.
